The problem

Payments must be right — every time

A bank processes a raw transaction and must decide, auditable, in order:

  • Is it well-formed? (fields, amount, currency)
  • Is it risky? (high-value, off-hours, cross-border)
  • Is it compliant? (reporting, sanctions)

…without ever losing money to rounding, leaking account numbers, or dropping a record.

Frame it as a decision chain that must be correct, safe, and fully auditable.
The idea

Two layers of agents

① Meta-agents — build the system

Spec → Code → Tests → Docs. Four AI roles that produce the pipeline.

② Runtime agents — run the bank

Validator → Fraud → Compliance. Three programs that process real transactions.

  Meta-agents  ═══build═══▶   Runtime pipeline   ═══process═══▶   Auditable outcome
  (Spec/Code/Tests/Docs)     (3 cooperating agents)            (approved / rejected)
This is the key mental model. The deliverable is BOTH the four builders and the running system.
Architecture

One integrator, three agents, four mailboxes

                     sample-transactions.json
                               │
                        ┌──────────────┐
                        │  integrator  │   run_pipeline()
                        └──────┬───────┘
                               ▼        wrap each record in a JSON envelope
       shared/input ─▶ processing ─▶ output ─▶ results     (a file's folder = its state)
                               │
   transaction_validator ─▶ fraud_detector ─▶ compliance_checker
           │ reject                                      │ approve / reject
           └─────────────────────┬────────────────────────┘
                                 ▼
             shared/results/<TXN>.json  +  summary.json  +  audit.log

A rejection short-circuits the rest — yet the transaction still lands in results/ with its reason.

Directory = state. Atomic file moves. Everything ends up in results/, even rejects.
How agents cooperate

They pass JSON files — nothing shared in memory

  • Standard envelope per message (id, timestamp, source, target, payload)
  • Atomic writes — temp file + os.replace; no half-written reads
  • The data block accumulates as it flows downstream
{
  "message_id": "uuid4…",
  "timestamp": "2026-03-16T10:00:00Z",
  "source_agent": "transaction_validator",
  "target_agent": "fraud_detector",
  "data": {
    "transaction_id": "TXN001",
    "amount": "1500.00", "currency": "USD",
    "status": "validated",
    "cross_border": false, "risk_score": 0
  }
}
File-based message passing makes the whole run inspectable and testable.
The runtime pipeline

Three agents, three decisions

Cross-border risk lives in fields separate from domestic risk — a reviewer sees why a txn was flagged.

Each agent is a pure function at its core (score_transaction, evaluate) — trivially unit-testable.
Correctness by construction

Banking-safe guarantees

  • 💰 Money is decimal.Decimal from string — never float
  • 💱 Currency is an ISO-4217 whitelist (XYZ → rejected)
  • 🔒 PII masked: ACC-1005 → ACC-**** before any log or result
  • 📝 Append-only audit log — ISO-8601 UTC, agent, txn id, outcome
