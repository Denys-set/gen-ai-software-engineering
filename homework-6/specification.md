> Generated by **Agent 1 (Specification)** via the `/write-spec` skill.
> Author: **Denys Kubrakov <dkbeetroot@gmail.com>**
> Stack: Python 3.11 · `decimal.Decimal` for money · file-based JSON message passing · pytest + pytest-cov.
> Emphasis note: **cross-border rules** are called out as first-class, independently testable

> checker).

---

## 1. High-Level Objective

Process raw banking transactions through a pipeline of cooperating agents — validation, fraud
scoring, and compliance decisioning — that pass JSON messages through shared directories, apply
heightened scrutiny to cross-border activity, and write an auditable `approved`/`rejected` outcome
for every transaction.

---

## 2. Mid-Level Objectives

Each objective is concrete and verifiable by a unit test, grounded in the 8 records of
`sample-transactions.json`. The **home jurisdiction is `"US"`**; any transaction where
`metadata.country != "US"` is cross-border.

1. **High-value fraud flag** — transactions above **$10,000** (e.g. `TXN002` $25,000, `TXN005`
   $75,000 wires) are flagged for fraud review with a numeric `risk_score`.
2. **Cross-border transactions are explicitly flagged and scored** — any transaction with
   `metadata.country != "US"` (`TXN004`, country `DE`; `TXN007`, country `GB`) is tagged
   `cross_border: true`, accrues a dedicated risk-score contribution, and carries a
   `cross_border_flags` list distinct from domestic risk flags — so cross-border risk is
   independently auditable, not folded silently into a generic score.
3. **Invalid input is rejected at validation** — a non-ISO-4217 currency (`TXN006` `"XYZ"`) and a
   non-positive amount (`TXN007` `-100.00` refund) are rejected before fraud/compliance ever run,
   each with a `reason`. (`TXN007` is thus a regression case: it is both cross-border *and*
   invalid — validation rejection must win, and the transaction must never reach the cross-border
   scoring path.)
4. **Cross-border transactions crossing the CTR threshold get compounded scrutiny** — a
   transaction that is *both* cross-border *and* off-hours (`TXN004`, `02:47Z` UTC, country `DE`)
   accrues risk points from **both** rules independently (off-hours + cross-border are additive,
   not mutually exclusive) and is routed to fraud review; compliance additionally attaches a
   cross-border compliance flag (e.g. enhanced due diligence) separate from the domestic
   currency-transaction-report (CTR) flag.
5. **Full auditability** — every agent operation (including cross-border determinations) is
   appended to an audit log with an **ISO-8601 UTC timestamp**, the agent name, the transaction id,
   and the outcome — and **all 8** input records appear in `shared/results/` after a run, each
   carrying an explicit `cross_border: true|false` field regardless of outcome.

## 3. Implementation Notes

Binding constraints the code MUST follow:

- **Money = `decimal.Decimal`, never `float`.** Amounts arrive as strings in the JSON
  (`"1500.00"`, `"25000.00"`) and must be parsed with `Decimal(str_value)`. All comparisons and
  arithmetic use `Decimal`; use `ROUND_HALF_UP` if rounding is ever needed.
- **Currency = ISO-4217 only.** Accept a whitelist of valid codes (USD, EUR, GBP, JPY, CHF, CAD,
  AUD, …). Reject anything not in the set (`"XYZ"` → rejected).
- **Cross-border determination is explicit, not incidental.** Define `HOME_COUNTRY = "US"` as a
  named constant (not a magic string scattered across agents). A transaction is cross-border iff
  `metadata.country != HOME_COUNTRY`. This check MUST be computed once and threaded through
  `data['cross_border']` (boolean) so every downstream agent and every result record can filter on
  it without recomputing it. Cross-border risk points and cross-border compliance flags MUST be
  tracked in fields separate from the generic/domestic ones (`cross_border_flags` vs. `risk_flags`,
  a `cross_border_review` flag distinct from `fraud_review`) so a reviewer can answer "was this
  flagged *because* it was cross-border?" from the record alone.
- **Audit log.** Every operation logs a record of
  `{timestamp (ISO-8601 UTC, e.g. 2026-03-16T10:00:00Z), agent, transaction_id, outcome}`.
  The log is the audit trail — it is append-only and machine-parseable (JSON lines).
- **PII protection.** `source_account`, `destination_account`, and any account holder names are
  sensitive. **Never log them in plaintext** — mask (e.g. `ACC-1001` → `ACC-****`) or hash before
  they touch the audit log or any printed summary. Transaction IDs (`TXN001`) are safe to log, and
  so is the `cross_border` boolean and `metadata.country` (jurisdiction is not PII).

## 4. Context

- **Beginning state:** `sample-transactions.json` — 8 raw transaction records with fields
  `transaction_id`, `timestamp`, `source_account`, `destination_account`, `amount` (string),
  `currency`, `transaction_type`, `description`, and `metadata.{channel,country}`. Two records
  (`TXN004`, `TXN007`) are cross-border (`country` != `US`); one of those (`TXN007`) is also
  invalid and must be rejected before cross-border scoring runs.
- **Ending state:**
  - Processed results in `shared/results/` — one JSON per transaction with final
    `status` (`approved` / `rejected`), `reason`, `risk_score`, and an explicit
    `cross_border` boolean + `cross_border_flags` list.
  - A **pipeline summary report** (`shared/results/summary.json`) — counts of
    approved/rejected/flagged outcomes **plus a cross-border count** (how many of the 8 records
    were cross-border, and how many of those were approved vs. rejected).
  - An **audit log** capturing every agent step, including cross-border determinations.
  - Unit-test **coverage ≥ 90%** (a hook hard-blocks push below **80%**), with explicit test cases
    for: a cross-border-but-valid transaction (`TXN004`), a cross-border-and-invalid transaction
    (`TXN007`), and domestic transactions (the other six) to prove the cross-border flag is never
    set incorrectly.

## 5. Low-Level Tasks

One block per component: the orchestrator plus three runtime agents.

```
Task: Integrator (Orchestrator)
Prompt: "Create agents/../integrator.py that sets up the shared/{input,processing,output,results}
         directories, loads sample-transactions.json, wraps each record in the standard message
         envelope (message_id, timestamp, source_agent, target_agent, message_type, data), and
         drops it into shared/input/. Then run the agents in order transaction_validator ->
         fraud_detector -> compliance_checker, moving each message input->processing->output
         between stages. A rejection at any stage short-circuits the remaining stages. Collect
         every final message into shared/results/<transaction_id>.json, write a summary.json with
         approved/rejected/flagged counts AND a cross_border count (total cross-border records,
         plus approved/rejected breakdown among them), and append every step to the audit log.
         Print a per-transaction summary (IDs, outcomes, and cross_border flag only — no account
         numbers)."
File to CREATE: integrator.py
Function to CREATE: run_pipeline(transactions_path: str = "sample-transactions.json") -> dict
Details: Orchestrates the file-based message flow; enforces short-circuit on rejection; guarantees
         all 8 transactions land in shared/results/ each carrying a cross_border boolean;
         produces summary.json (with cross-border breakdown) + audit log.
```

```
Task: Transaction Validator
Prompt: "Create agents/transaction_validator.py exposing process_message(message: dict) -> dict.
         Validate the transaction in message['data']: (1) all required fields present
         (transaction_id, amount, currency, source_account, destination_account, timestamp,
         metadata.country); (2) amount parses as a positive decimal.Decimal (reject <= 0, e.g.
         -100.00); (3) currency is a valid ISO-4217 code (reject 'XYZ'). Regardless of outcome,
         compute and attach data['cross_border'] = (metadata.country != 'US') so downstream agents
         never recompute it. On success set data['status']='validated' and route to
         fraud_detector; on failure set status='rejected' with a reason string — a rejection here
         (e.g. TXN007's negative amount) must short-circuit before any cross-border risk scoring
         happens, even though TXN007 is itself cross-border (country GB). Never log account
         numbers in plaintext. Support a --dry-run CLI mode that validates every record in
         sample-transactions.json and prints total/valid/invalid counts with reasons, including
         how many of the invalid records were cross-border."
File to CREATE: agents/transaction_validator.py
Function to CREATE: process_message(message: dict) -> dict
Details: Rejects TXN006 (currency 'XYZ') and TXN007 (amount -100.00, despite being cross-border);
         passes the other six, tagging TXN004 and TXN007 with cross_border=true and the rest
         cross_border=false. Enforces Decimal parsing, ISO-4217 whitelist, required-field
         presence, PII masking.
```

```
Task: Fraud Detector
Prompt: "Create agents/fraud_detector.py exposing process_message(message: dict) -> dict. Compute a
         numeric risk_score from additive rules: high-value amount > $10,000 (+50), off-hours UTC
         timestamp with hour in [0,6) (+20), and cross-border (data['cross_border'] is True, set by
         the validator) (+20). These rules are independent and additive — a transaction that is
         both off-hours AND cross-border (TXN004) accrues both contributions. Track cross-border
         risk separately: append to a dedicated data['cross_border_flags'] list (distinct from the
         general data['risk_flags']) whenever the +20 cross-border points are applied, so a
         reviewer can see the cross-border contribution to risk_score in isolation. If risk_score
         >= a review threshold (50) set data['fraud_review']=True; additionally, if
         data['cross_border'] is True set data['cross_border_review']=True regardless of the
         combined score, so cross-border activity is always visible to the next stage even when it
         alone wouldn't trip the domestic threshold. Route validated+scored messages to
         compliance_checker. Money comparisons use decimal.Decimal. Log only transaction_id +
         outcome + cross_border boolean (no PII)."
File to CREATE: agents/fraud_detector.py
Function to CREATE: process_message(message: dict) -> dict
Details: Flags TXN002/TXN005 (high-value, domestic), TXN004 (off-hours +20 AND cross-border +20 =
         40 combined, cross_border_review=True regardless of total). Produces risk_score,
         risk_flags, and a separate cross_border_flags list; sets fraud_review above threshold and
         cross_border_review whenever cross_border is true.
```

```
Task: Compliance Checker
Prompt: "Create agents/compliance_checker.py exposing process_message(message: dict) -> dict. Apply
         compliance rules on the validated, fraud-scored message: (1) currency-transaction report
         threshold — amount >= $10,000 requires a CTR flag; (2) sanctions screening — reject if
         source/destination account, OR data['cross_border'] country, is on a (configurable)
         sanctions/restricted-country list; (3) cross-border enhanced due diligence — if
         data['cross_border'] is True, attach a dedicated compliance flag
         'cross_border_edd' (enhanced due diligence) to data['compliance_flags'], independent of
         the CTR flag, so cross-border and high-value scrutiny are auditable separately even when
         both apply to the same transaction; (4) decision — reject when sanctions hit or
         risk_score is critical (>= 70), otherwise approve (cross-border alone, absent a sanctions
         hit or critical score, does not force rejection — it forces visibility, not automatic
         denial). Set final data['status'] to 'approved' or 'rejected' with a reason, attach
         compliance_flags (including cross_border_edd where applicable), and route the message to
         shared/results/. Never log account numbers in plaintext; country codes are not PII and
         may be logged."
File to CREATE: agents/compliance_checker.py
Function to CREATE: process_message(message: dict) -> dict
Details: Produces the terminal approved/rejected decision + reason; adds CTR flag for >= $10k and a
         separate cross_border_edd flag whenever cross_border is true (e.g. TXN004); supports a
         sanctions/restricted-country list; writes the final outcome consumed by the integrator.
```
